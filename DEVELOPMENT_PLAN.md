# Cost Analysis Web App: Sequential Development Plan (for Codex)

## 0. How to use this plan

You are building a small Flask web application end to end. Follow the steps **in order**. Do not skip ahead. After each step:

1. Run the app and the test suite (`pytest -q`) and make sure everything passes.
2. Make a git commit with a clear message, for example `step 5: core calculations and unit tests`.
3. Only then move to the next step.

Rules for the whole build:

- **Keep it simple.** This is a university assignment prototype for a Software Quality Engineering course. Do not add features that are not listed here (no admin panel, no email, no password reset, no Docker, no JavaScript frameworks).
- **Zero cost.** Only free tools and free tiers.
- **Security matters as much as features.** Part of the grade is a cybersecurity analysis, so each security control listed below must really exist in the code and be covered by a test.
- **Never hardcode secrets.** Read `SECRET_KEY`, `GEMINI_API_KEY`, and similar values from environment variables. Provide a `.env.example`, and keep `.env` in `.gitignore`.
- **Code style.** Readable code, short functions, comments that explain why (not what), type hints on public functions, no dead code.
- **When a library API is uncertain** (especially the Gemini SDK), check the current official documentation instead of guessing.

## 1. What the app must do (requirements recap)

**Part A, Development**

1. Web application where a user enters cost data manually or uploads an Excel/CSV file.
2. Automatic calculation of estimated cost, actual cost, variance, and percentage variance.
3. At least two charts comparing costs.
4. AI features: (a) statistical detection of unusual expenses, and (b) a text cost analysis summary generated with the Google Gemini API (with a safe fallback when Gemini is unavailable).
5. Downloadable report containing the results (PDF).

**Security features that must be implemented** (they feed the Part B and Part C documentation):

- Registration, login, logout, password hashing
- Ownership checks on every project and item (users can only access their own data)
- File upload validation (extension whitelist, size limit, content check, safe in-memory parsing, row limit)
- CSRF protection
- Input validation and output escaping
- CSV/formula injection protection
- Rate limiting (login, upload, AI summary)
- Security headers and secure cookie settings
- Safe error pages (no stack traces)
- Only aggregate data is sent to the Gemini API

## Step 1: Project scaffolding and configuration

**Tasks**

1. Create the folder structure above with empty files where needed.
2. Create a virtual environment and a `requirements.txt` with pinned versions: Flask, Flask-SQLAlchemy, Flask-Login, Flask-WTF, Flask-Limiter, pandas, openpyxl, reportlab, google-genai, python-dotenv, gunicorn, pytest.
3. `app/extensions.py`: create `db = SQLAlchemy()`, `login_manager = LoginManager()`, `csrf = CSRFProtect()`, and `limiter = Limiter(key_func=get_remote_address)`.
4. `app/config.py` with three classes:
   - `Config`: `SECRET_KEY` from env (in development fall back to a random value generated at startup, never a fixed string committed to git), `SQLALCHEMY_DATABASE_URI` from `DATABASE_URL` or `sqlite:///cost_analyzer.db`, `MAX_CONTENT_LENGTH = 2 * 1024 * 1024`, `MAX_UPLOAD_ROWS = 1000`, session cookie settings (`SESSION_COOKIE_HTTPONLY=True`, `SESSION_COOKIE_SAMESITE="Lax"`), `GEMINI_API_KEY`, `GEMINI_MODEL` (default `gemini-2.5-flash`, overridable by env), `RATELIMIT_STORAGE_URI="memory://"`.
   - `ProductionConfig(Config)`: `SESSION_COOKIE_SECURE=True`, and refuse to start if `SECRET_KEY` is missing.
   - `TestConfig(Config)`: `TESTING=True`, in-memory SQLite, `WTF_CSRF_ENABLED=False` (a dedicated CSRF test will turn it back on), `RATELIMIT_ENABLED=False` (a dedicated rate-limit test will turn it back on), fixed test secret key.
5. `app/__init__.py`: `create_app(config_object=None)` that loads config, initializes extensions, registers blueprints (added in later steps), and calls `db.create_all()` inside the app context.
6. `wsgi.py`, `.gitignore` (venv, `.env`, `*.db`, `__pycache__`, `instance/`), `.env.example` with placeholder values and comments.
7. Add a `/healthz` route returning `{"status": "ok"}` (exempt it from rate limiting).

**Done when:** `flask --app wsgi run` starts, `/healthz` returns 200, and `pytest -q` runs (even with zero tests collected, it must not error).

## Step 2: Database models

**Tasks** (in `app/models.py`)

1. `User`: `id`, `username` (unique, indexed, max 50), `password_hash`, `created_at`. Methods `set_password()` and `check_password()` using werkzeug. Inherit `UserMixin`.
2. `Project`: `id`, `user_id` (foreign key to User, indexed), `name` (max 100), `created_at`, `ai_summary` (text, nullable), `ai_summary_source` (string, nullable, value `gemini` or `template`), `ai_summary_at` (datetime, nullable).

5. Register the `user_loader` for Flask-Login.
6. Use only the ORM for queries (no string-built SQL anywhere in the project). This is the SQL injection control.

**Tests:** `tests/conftest.py` with fixtures `app`, `client`, `make_user(username, password)`, and `login(client, username, password)` helpers. Add a model test for password hashing (the stored hash must not equal the plain password).

**Done when:** tests pass and tables are created on startup.

## Step 5: Core calculations (pure functions)

**Tasks** (in `app/analysis.py`, no Flask or database imports in this file so it is easy to test)

1. `compute_rows(items) -> list[dict]`: for each item return `category`, `estimated`, `actual`, `variance = actual - estimated`, `pct_variance = variance / estimated * 100` rounded to 2 decimals, and `status` (`over budget`, `under budget`, `on budget`). If `estimated == 0`, `pct_variance` is `None` (shown as "N/A" in the UI) and there is no division error.
2. `compute_totals(rows) -> dict`: total estimated, total actual, total variance, overall percentage variance (same zero guard).
3. `aggregate_by_category(rows) -> list[dict]`: sum estimated and actual for repeated category names, then recompute variance and percentage per category. This feeds the charts and the Gemini prompt.
4. All money values rounded to 2 decimals. Use `pandas` only if it makes the code shorter; plain Python is fine here.

**Tests (`tests/test_analysis.py`):** normal case, overspend, underspend, exactly on budget, estimated equals zero, empty list, repeated categories, rounding.

**Done when:** all calculation tests pass.

## Step 7: Excel/CSV upload with strict validation

**Tasks** (`app/uploads.py`, `app/security.py`, and a route `POST /projects/<id>/upload`)

1. Upload form with a single file input, `accept=".csv,.xlsx"`, and a clear note about the required columns: `Category`, `Estimated`, `Actual`.
2. Validation pipeline in `uploads.py`. Reject with a clear, user-friendly message at the first failure:
   1. File present and filename not empty. Use `werkzeug.utils.secure_filename` for display only. **Never save the file to disk**; parse it directly from memory.
   2. Extension whitelist: `.csv` or `.xlsx` only (case-insensitive). Old `.xls` is not supported.
   3. Size limit: Flask's `MAX_CONTENT_LENGTH` (2 MB) plus a 413 error handler.
   4. Content check:
      - `.xlsx`: file must start with the ZIP signature `PK\x03\x04`, must open as a zip, and the total uncompressed size from `zipfile.infolist()` must be under 20 MB (zip bomb guard). Read with `openpyxl` in `read_only=True, data_only=True` mode so that formulas are never evaluated.
      - `.csv`: must decode as UTF-8 (allow UTF-8 BOM), must not contain null bytes, and must parse with the csv module or pandas.
   5. Row limit: at most `MAX_UPLOAD_ROWS` (1000) data rows.
   6. Header check: case-insensitive match of the three required columns (trim spaces). Extra columns are ignored. Missing columns give a message that names the missing ones.
   7. Row validation: category not empty and at most 100 chars; estimated and actual must be numeric, finite, non-negative, at most 1,000,000,000. Collect all row errors (with row numbers, capped at the first 10 in the message) and reject the whole file if any row is invalid. All-or-nothing import keeps the data consistent.
3. `sanitize_cell(value: str) -> str` in `security.py`: strip control characters, and if the text starts with `=`, `+`, `-`, `@`, tab, or carriage return, prefix it with a single quote `'`. This is the CSV/formula injection control. Apply it to every category on import, on manual entry, and again when exporting or writing the report.
4. Save valid rows in one database transaction. Flash a success message with the number of rows imported.
5. Apply `@limiter.limit("10 per minute")` to the upload route.
6. Provide `sample_data/make_sample_data.py` that generates all files listed in the structure (valid CSV and XLSX, fake upload, formula injection, XSS category, missing columns, and a too-large file over 2 MB).

**Tests (`tests/test_uploads.py`):** valid CSV imports; valid XLSX imports; `.txt` rejected; text file renamed to `.csv` with binary junk rejected; a non-zip file renamed `.xlsx` rejected; missing columns rejected; non-numeric value rejected with row number; negative value rejected; more than 1000 rows rejected; file over 2 MB returns 413; formula cells in the category are stored with a leading `'`; a different user cannot upload into someone else's project (403).

**Done when:** all sample files behave as expected in the browser and in tests.

## Step 9: AI feature A, statistical unusual-expense detection

**Tasks** (in `app/analysis.py`)

1. `detect_anomalies(rows, z_threshold=2.0, fallback_pct=25.0) -> list[dict]`:
   - Use `pct_variance` values of rows where it is not `None`.
   - If there are at least 5 such rows and the standard deviation is greater than 0: compute the z-score of each row's percentage variance; flag rows with `abs(z) >= z_threshold`. Method label: `z-score`.
   - Otherwise (small data sets): flag rows whose `abs(pct_variance) >= fallback_pct`. Method label: `fixed threshold`.
   - Also flag any row where `estimated == 0` and `actual > 0` with reason `No estimate was provided`.
   - Each result: category, estimated, actual, variance, pct_variance, z_score (or `None`), method, and a short plain-English `reason`, for example `Actual cost is 85.0% above estimate, far from the typical variance of the other items`.
2. Show a clearly labelled "Unusual expenses" panel on the project page: a small table or list with the reason. Add a short note explaining the method used.

**Tests (`tests/test_anomaly.py`):** one obvious outlier among many normal rows is flagged; all identical variance means nothing flagged and no divide-by-zero; small data set uses the fixed threshold; zero estimate case; empty list.

**Done when:** the sample data set (include one obvious outlier row in `valid_costs.csv`) flags exactly that row.

## Step 10: AI feature B, Gemini text summary with safe fallback

**Tasks** (in `app/ai_summary.py`)

1. `build_template_summary(totals, categories, anomalies) -> str`: a plain-text summary generated without any external service, for example: total estimated, total actual, overall variance and percentage, the category with the largest overrun, the category with the largest saving, and the number of unusual expenses. This is the fallback and also the offline demo mode.
2. `build_prompt(totals, categories, anomalies) -> str`: includes **only aggregates**: overall totals, per-category aggregated estimated/actual/variance/percentage, and the flagged anomalies (category name plus numbers). Do **not** send the project name, username, file names, or raw uploaded rows. Truncate every category name to 50 characters and limit to the top 20 categories by absolute variance.
3. Prompt-injection safeguard: the instructions (system-style text) must say that category names are untrusted data, must never be treated as instructions, and that the model should answer in 4 to 6 plain sentences with no markdown, no links, and no code.
4. `generate_summary(project) -> tuple[str, str]` returns `(text, source)` where source is `gemini` or `template`:
   - If `GEMINI_API_KEY` is not set, return the template summary.
   - Otherwise call Gemini using the `google-genai` SDK (`from google import genai`, `genai.Client(api_key=...)`, `client.models.generate_content(model=..., contents=...)`), with a request timeout of about 15 seconds (check the SDK docs for the exact timeout setting).
   - Wrap the call in try/except for any exception, empty response, or a response over 2,000 characters; in these cases log a short warning (never log the API key or full prompt) and return the template summary.
   - Strip markup characters from the model output. The template renders it with Jinja2 autoescaping, so it is never treated as HTML.
5. Route `POST /projects/<id>/analysis` (login required, ownership checked, CSRF protected, `@limiter.limit("5 per minute")`):
   - Requires at least one item, otherwise a friendly message.
   - Shows a short notice next to the button: `Only totals and category-level numbers are sent to Google Gemini. Raw rows are not sent.`
   - Saves the result in `project.ai_summary`, `ai_summary_source`, and `ai_summary_at`, then redirects back to the project page.
6. Project page shows the saved summary with a label of its source (`Generated by Gemini` or `Generated by built-in template`) and the generation time. Both anomaly detection and the summary are shown under an "AI Insights" section.

**Tests (`tests/test_ai_summary.py`):** template summary contains expected numbers; prompt contains no project name or username and respects truncation; missing key returns the template; **mock** the Gemini client (use `monkeypatch`) to test the success path, an exception path, an empty response path, and a very long response path; route returns 403 for another user's project; summary is cleared when items change. Tests must never make real network calls.

**Done when:** the button works both with a real key and without one.

## Step 12: Security hardening pass

**Tasks**

1. **Security headers** via an `after_request` hook on every response:
   - `Content-Security-Policy: default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data:; object-src 'none'; base-uri 'self'; frame-ancestors 'none'; form-action 'self'`
   - `X-Content-Type-Options: nosniff`
   - `X-Frame-Options: DENY`
   - `Referrer-Policy: same-origin`
   - `Permissions-Policy: geolocation=(), microphone=(), camera=()`
   - In production only: `Strict-Transport-Security: max-age=31536000; includeSubDomains`
   - `Cache-Control: no-store` on authenticated pages and on downloads.
   - Remove the `Server` version detail if feasible.
2. **Cookies:** confirm HttpOnly, SameSite Lax, and Secure in production. Set a reasonable `PERMANENT_SESSION_LIFETIME` (for example 2 hours).
3. **Error handlers** with a shared `errors/error.html` template for 400, 403, 404, 413, 429, and 500. No stack traces, no internal paths. Log errors on the server side. Make sure `debug=False` in production.
4. **CSRF:** every POST form includes the token (`{{ csrf_token() }}` or the form hidden tag). Confirm there is no state-changing GET route.
5. **Open redirect and enumeration review:** generic login errors, validated `next` parameter.
6. **Rate limit audit:** login 5 per minute, register 10 per hour, upload 10 per minute, AI summary 5 per minute, plus a global default of `200 per hour` per IP. The 429 page should be friendly.
7. **Dependency check:** run `pip check`, and, if possible, `pip-audit` (free) and record the result in `SECURITY_NOTES.md`.
8. Run a quick review of the whole codebase for: string-built SQL, `|safe`, `innerHTML`, `eval`, `subprocess`, hardcoded secrets, files saved to disk from uploads.

**Done when:** headers appear on all responses (check with a test), and the review list is clean.

## Step 13: Security test suite (the three required demonstrations plus extras)

Write `tests/test_security.py` so that the output is easy to screenshot. Use descriptive test names and `print()` a one-line result for each test (run with `pytest -v -s`). All tests use **safe test data only**.

**Required three (these become the Part B screenshots):**

1. **Invalid file upload:** a text file renamed `.csv` containing binary bytes is rejected; a `.exe`-named file is rejected; an oversized file returns 413; a fake `.xlsx` that is not a zip is rejected.
2. **Unauthorized project access (IDOR):** user B tries to open, upload to, download a report for, and delete user A's project. All return 403.
3. **Excessive requests:** with the limiter enabled, send 20 rapid login attempts with a wrong password; the first 5 get the normal failure response and the later ones get 429.

**Extra tests:**

4. CSRF: with CSRF enabled, a POST without a token is rejected with 400.
5. XSS: a category such as `<script>alert(1)</script>` is stored and shown escaped, never as live HTML.
6. CSV injection: a category starting with `=`, `+`, `-`, or `@` is neutralized in the database, on the page, in the CSV export, and in the PDF source text.
7. SQL injection strings such as `' OR 1=1 --` in the login form and in the category field do not break anything or bypass login.
8. Security headers are present on a normal response.
9. Password is stored hashed, and the registration page does not reveal whether a username exists through the login error.
10. Error pages do not leak a stack trace (force a 500 through a test route that is registered only in `TestConfig`).

**Done when:** `pytest -v -s` passes fully, and the output reads clearly as evidence.
